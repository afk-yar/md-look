# 005-ссылки-и-картинки: Исправить ссылки и локальные картинки

**Контекст:** MDLook рендерит исходный Markdown не из его исходной папки, а из временного HTML-файла. Поэтому относительные URL в Markdown не имеют корректной базы: ссылки на файлы и `img src` ведут не туда, а внешние ссылки не имеют явного управляемого поведения внутри WebView.

**Найденные примеры и пробелы входных данных:**
- Межфайловые Markdown-ссылки (`[...](other.md)` / `[...](../dir/other.md#anchor)`) в текущем корпусе, без учета этой feature-задачи и будущих fixtures, не найдены. Проверка `rg -n -g "*.md" -g "!tasks/005-ссылки-и-картинки/tasks.md" "\]\([^)]*\.md(?:#[^)]*)?\)" .` вернула 0 совпадений. Это отдельный сигнал возможной ошибки скрапера: сценарий навигации между `.md` файлами нельзя подменять примером ссылки на `app.py`.
- Generic local file link, не заменяющий межфайловую Markdown-ссылку: `tasks/001-несколько-окон/tasks.md:5` - `[Реверс app.py](../../app.py)`.
- Внешние ссылки: `tasks/001-несколько-окон/tasks.md:5` - `[pywebview multi-window](https://pywebview.flowrl.com/3.7/guide/usage)`, `[js_api per-window](https://pywebview.flowrl.com/guide/interdomain.html)`.
- Картинки: в Markdown-синтаксисе `![...](...)` примеров в текущих `.md` нет, но в проекте есть реальные локальные ассеты `docs/architecture-assets/architecture-whiteboard.png` и `docs/architecture-assets/architecture-isometric.png`. Их нужно использовать в отдельном репродьюсере `docs/links-images-repro.md`, например строкой `![whiteboard](architecture-assets/architecture-whiteboard.png)`.

**Технические факты:**
- `app.py:1248` уже передает папку исходного Markdown в шаблон через `MDFOLDER_PLACEHOLDER`, а `MDLook-template-offline.html:4452` читает ее как `embeddedFolder`.
- `app.py:1260` пишет temp HTML через `tempfile.mkstemp(...)`, а `app.py:1503` / `app.py:1575` загружают именно этот temp-файл как `file:///...`.
- `MDLook-template-offline.html:4102` рендерит картинки как `<img src="$2" alt="$1">` без экранирования и без перевода относительного пути в URL от папки исходного `.md`.
- `MDLook-template-offline.html:4106` и `4121` рендерят обычные и автоссылки с `target="_blank"`, но `app.py:778` перехватывает только `a[href^="#"]`.
- Proof: MDN описывает, что base URL используется при разрешении относительных URL для `img src` и `href`: https://developer.mozilla.org/en-US/docs/Web/API/Node/baseURI. MDN по `<base>`: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/base.
- 2026-07-02 manual-verification trap: если уже запущен старый установленный `C:\Program Files\MDLook\MDLook.exe`, запуск свежего `dist/MDLook/MDLook.exe` может передать файл старому процессу через single-instance IPC. Признак: temp HTML для `docs/links-images-repro.md` не содержит `resolveMdUrl`, а ссылка открывается как `%TEMP%/linked-note.md`. IPC нужно scope-ить по identity исполняемого файла.

## Подробно

### T-01. Ввести единый resolver URL от папки исходного Markdown [M] <a id="t-01"></a>

**Проблема.** Сейчас `parseInline()` отдает `href` и `src` почти как написано в Markdown. Для HTML, загруженного из `%TEMP%`, относительные пути будут интерпретироваться относительно temp HTML, а не относительно исходного `.md` файла.

**Что сделать:**
1. В `MDLook-template-offline.html` завести единый JS-helper для URL из Markdown, например `resolveMdUrl(rawUrl, kind)`, где `kind` отличает `link` от `image`.
2. Helper должен отличать:
   - `#anchor` - оставить как hash без преобразования;
   - `http://`, `https://`, `mailto:` - оставить как внешние/абсолютные URL;
   - `data:` - разрешить только для `kind === 'image'`, для кликабельных ссылок не исполнять;
   - `file://...` - оставить абсолютным file URL после минимальной валидации;
   - Windows absolute path (`C:\...`) и UNC path (`\\server\share\...`) - перевести в корректный `file:///...`;
   - относительный путь - собрать от `folderFromPath(filePath)` или `embeddedFolder`.
3. Вынести escaping URL-атрибутов в отдельный helper, чтобы не собирать HTML-атрибуты сырыми строками.
4. Не менять поведение Markdown-парсера шире этой задачи: не добавлять полноценный CommonMark parser, не поддерживать весь синтаксис link title.

**Критерий готовности:**
1. Для тестового файла `docs/links-images-repro.md` ссылка `[Связанный документ](linked-note.md#target)` превращается в URL к реальному `docs/linked-note.md#target`, а не к пути относительно temp HTML.
2. Hash-ссылки продолжают рендериться как `href="#..."`.
3. `http`, `https` и `mailto` не искажаются.
4. `data:` разрешается для картинок и не становится исполняемой ссылкой.
5. Пути с пробелами и кириллицей кодируются в корректный URL.

**Файлы:** `MDLook-template-offline.html`

### T-02. Нормализовать поведение кликов по ссылкам [M] <a id="t-02"></a>

**Проблема.** Внутренние hash-ссылки частично обработаны в `BRIDGE_JS`, но внешние и файловые ссылки отданы браузеру через `target="_blank"`. Для desktop-приложения это неявное поведение: пользователь ожидает, что внешняя ссылка откроется в системном браузере, а локальная ссылка на файл будет открыта предсказуемо.

**Что сделать:**
1. Добавить в `Api` метод для открытия внешних/локальных URL через системное действие:
   - внешние `http/https/mailto` - системный браузер/почтовый клиент;
   - локальные `file://` или абсолютные пути - системное действие Windows;
   - локальные `.md`, `.markdown`, `.txt` - открыть в MDLook через существующий `_create_window()` или IPC-путь, без замены текущего окна.
2. В `BRIDGE_JS` добавить click-handler для ссылок после существующего hash-handler:
   - `#...` остается внутри WebView и использует текущую smooth-scroll логику;
   - остальные ссылки вызывают Python API и делают `preventDefault()`;
   - неизвестные или потенциально опасные схемы не исполняются.
3. Сохранить текущую работу About modal и служебных ссылок шаблона.

**Критерий готовности:**
1. Клик по `[pywebview multi-window](https://pywebview.flowrl.com/3.7/guide/usage)` из `tasks/001-несколько-окон/tasks.md` открывает системный браузер, а не пытается навигировать temp WebView.
2. Клик по `[Связанный документ](linked-note.md#target)` из `docs/links-images-repro.md` открывает `docs/linked-note.md` в новом окне MDLook и передает hash/target для перехода.
3. Клик по generic local file link вроде `[Реверс app.py](../../app.py)` открывает реальный локальный файл через системное действие, но этот кейс не считается проверкой `.md`-к-навигации.
4. Клик по `#anchor` продолжает скроллить внутри текущего документа.
5. `data:` и схемы вне разрешенного списка не выполняются как кликабельные ссылки.

**Файлы:** `app.py`, `MDLook-template-offline.html`

### T-03. Починить отображение локальных картинок [M] <a id="t-03"></a>

**Проблема.** Markdown-картинки сейчас рендерятся как `<img src="$2" alt="$1">`. Относительный `src` не резолвится от папки исходного Markdown, поэтому локальные картинки рядом с документом не отображаются. Дополнительно `alt` и `src` вставляются без безопасного attribute escaping.

**Что сделать:**
1. Перевести markdown image renderer на helper из T-01: `![alt](relative/path.png)` должен получать корректный `file:///...` URL.
2. Экранировать `alt` и `src` как HTML-атрибуты.
3. Сохранить поддержку абсолютных `file` и `data` URL; `http/https` URL оставлять без искажения, но не строить на них offline-гарантию.
4. Добавить ограниченный visual fallback: если картинка не загрузилась, показывать аккуратный inline-блок с `alt` и исходным путем, чтобы пользователь видел, что ресурс не найден.
5. Не вводить загрузку внешних ресурсов поверх текущего offline-подхода; задача только исправляет уже указанную ссылку на изображение.

**Критерий готовности:**
1. В Markdown-файле из папки `docs/` строка `![whiteboard](architecture-assets/architecture-whiteboard.png)` отображает `docs/architecture-assets/architecture-whiteboard.png`.
2. `![isometric](architecture-assets/architecture-isometric.png)` отображает вторую локальную картинку.
3. Путь с пробелом или кириллицей в имени файла корректно кодируется.
4. Несуществующая картинка не ломает верстку и дает понятный fallback.
5. Data URL продолжает рендериться; HTTP-картинка сохраняет исходный URL, но ручная проверка не требует доступной сети.

**Источник:** локальные ассеты для проверки: `docs/architecture-assets/architecture-whiteboard.png`, `docs/architecture-assets/architecture-isometric.png`

**Файлы:** `MDLook-template-offline.html`

### T-05. Проверить отсутствие межфайловых Markdown-ссылок как дефект скрапера [S] <a id="t-05"></a>

**Проблема.** В текущем наборе `.md` файлов нет ни одной ссылки на другой `.md` файл. Для задачи "работа со ссылками между файлами" это не нейтральный факт, а возможный дефект скрапера или входного корпуса: ссылки могли быть потеряны, переписаны или не попали в выгрузку.

**Что сделать:**
1. Зафиксировать inventory локальных ссылок по корпусу: Markdown links, HTML `href`, отдельно ссылки на `.md`/`.markdown`; тестовые fixtures и этот `tasks.md` считать отдельно от реального корпуса.
2. Проверить, есть ли в репозитории код или конфигурация скрапера. Если их нет, явно записать, что причина отсутствия межфайловых ссылок не может быть исправлена внутри этого репозитория без исходного pipeline.
3. Если скрапер/исходник доступен в соседнем проекте или артефактах, проверить, сохраняет ли он `href` между страницами при конвертации в Markdown.
4. Не использовать `tasks/001-несколько-окон/tasks.md:5` как пример межфайловой Markdown-навигации: ссылка на `app.py` покрывает только generic local file link.
5. До появления реальных примеров создать синтетический repro: `docs/links-images-repro.md` -> `docs/linked-note.md#target`.
6. Зафиксировать ERP-WE эталон как требование к скраперу/нормализатору: `0088_2._Планирование.md:7` `/db/erpwedoc/content/12/hdoc` должен стать ссылкой на `0089_2.1._Позиционирование_товарного_планирования.md`, но MDLook runtime не должен содержать правила для `/db/erpwedoc/...`.

**Критерий готовности:**
1. В задаче/отчете есть точный результат inventory: сколько найдено `.md`-ссылок и где, отдельно для реального корпуса и тестовых fixtures.
2. Если count = 0, это помечено как подозрение на проблему скрапера, а не как доказательство отсутствия требования.
3. Есть минимальный repro с двумя `.md` файлами, который проверяет именно переход между файлами.
4. Найденные реальные примеры, если они появятся после исправления скрапера, добавлены в `docs/links-images-repro.md` или отдельный fixture без замены синтетического минимального кейса.
5. ERP-WE эталон сохранен как documented evidence для будущей нормализации Markdown, но не попал в generic URL resolver MDLook.

**Файлы:** `tasks/005-ссылки-и-картинки/tasks.md`, `docs/links-images-repro.md`, `docs/linked-note.md`
